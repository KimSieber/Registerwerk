# Registerwerk v0.0.8: Entwicklungsdokumentation

Stand: 22.11.2026. Diese Datei hält fest, was Version 0.0.8 enthält, wie sie entstanden ist und welche Entscheidungen dabei gefallen sind. Die übergreifenden Festlegungen stehen im [Konzept](konzept.md). Konkrete Pfade und Messungen auf Kims Geräten stehen nicht hier, sondern in `docs/intern/` (nicht versioniert).

## 1. Ziel der Version

v0.0.8 macht aus dem Reiter „Register“ einen klaren Ablauf (Beginn von Stufe 4): Beim Öffnen prüft Registerwerk, was ansteht, zeigt es übersichtlich und verarbeitet die Auswahl nach einem Klick durch alle Schritte. Dazu gehören das Laden von „nur online“-Dateien aus der Dropbox und das Zurückstellen danach. Außerdem werden die Vorschau-Scheiben kleiner, weil das Register jetzt in der Dropbox liegt.

| Enthalten | Nicht enthalten |
|---|---|
| Prüfung beim Öffnen (Deltaanalyse), Zahl am Reiter „Register“ | Sperre mit Stand-Zähler |
| Zahlen für neu, geändert, offen, nur online, nur mit Namen, zu entfernen. Jede Zahl öffnet die Dateiliste | Erkennen verschobener Dateien per Inhalts-Hash |
| Ordnerbaum mit Haken, alles vorausgewählt, Schalter für alle „nur online“-Dateien | Verschlüsselung |
| „Verarbeiten“: aufnehmen, laden, Inhalte, Vorschauen, OCR, Textebene, zurück auf „nur online“, Suchindex | Reiter „Ordner“ ohne eigenes „Dateibaum einlesen“ (v0.0.9) |
| Laden über die Dateikoordination von macOS, gemeinsames Warten, „Nicht warten, weiter“ | Laden und Auslagern bei Google Drive, OneDrive, iCloud |
| Zurück auf „nur online“ mit `onlineonly` | `onlineonly` als Beigabe im Programmpaket |
| Entfernen als eigener Schritt mit Rückfrage | |
| Bisherige Ansicht unter „Einzelheiten und einzelne Schritte“ | |
| Scheiben bis 200 MB, Knopf „Scheiben aufteilen“ | |
| TIFF mit Farbpalette | |
| Platzhalter des File Providers (`SF_DATALESS`) | |
| Build-Ordner `target/cargo` | |

## 2. Ergebnis

- Schema unverändert 9. Neues Merkmal `tiff_palette` (einmaliges Zurücksetzen der gescheiterten Palette-TIFFs). Verfahrensversionen unverändert.
- Tests: 119 im Kern, 5 in `registerwerk-ocr`. `registerwerk-macos` wird für `aarch64-apple-darwin` geprüft (`cargo check`), Tests laufen bei Kim auf dem Mac.
- Bei Kim auf dem Notebook:
  - **Scheiben aufteilen** hat funktioniert. Die alte Scheibe von 1,3 GB ist auf Scheiben zu rund 200 MB verteilt. Vorher an einer gleich großen Testkopie geprüft: 38.498 Vorschauen in 7 s auf 7 Scheiben verteilt, jede Vorschau danach Byte für Byte gleich.
  - **TIFF mit Farbpalette** aus dem Altarchiv (Scans von 2003) werden gelesen, die Vorschau stimmt.
  - **Delta-Lauf** mit Laden aus der Dropbox getestet.
  - **Zurück auf „nur online“** mit `onlineonly` nur im Terminal an einer Datei geprüft, in der Anwendung bei Abschluss der Version noch nicht.
- Die Annahme aus dem Konzept „Öffnen löst den Download aus“ war falsch (Abschnitt 6).

### Abgleich in drei Modi

`Register::abgleich` kennt jetzt drei Modi:

| Modus | Aufruf | Wirkung |
|---|---|---|
| voll | `abgleichen` | aufnehmen, ändern, entfernen |
| Probe | `abgleich_pruefen`, `delta_pruefen` | wie voll, die Transaktion wird verworfen |
| nur aufnehmen | `aufnehmen` | neue und geänderte Dateien, nichts entfernen, keine Inhalte zurücknehmen. Eine Stufe, die auf „Nur Namen“ wechselt, bleibt bis zum bestätigten Entfernen stehen |

### Deltaanalyse

`delta_pruefen` läuft als Probe. Bevor die Transaktion verworfen wird, liest es, bei welchen Dateien ein Schritt ansteht (Inhalt, Vorschau, OCR, Textebene, als Bits). Neue Dateien sind dabei schon eingefügt, ihre Schritte zählen also mit. Jede Datei bekommt eine Art:

| Art | Bedeutung |
|---|---|
| neu | das Register kannte den Pfad nicht |
| geändert | Größe oder Datum weichen ab |
| offen | unverändert, aber ein Schritt steht noch aus (abgebrochen, nur online, neues Verfahren) |

Neue Dateien ohne anstehenden Schritt (nur mit Namen) werden getrennt gezählt und lassen sich ebenfalls ansehen.

OCR und Textebene einer neuen Datei zeigen sich erst, wenn ihr Inhalt gelesen ist. Im Lauf werden sie trotzdem erledigt, weil die Auswahl die Datei enthält.

Das Ergebnis bleibt in der Tauri-Hülle (`DeltaStand`). Die Oberfläche bekommt die Zahlen und alle Ordner mit ihren Zahlen. Die Dateien holt sie je Ordner beim Aufklappen (`delta_dateien`) oder als Liste je Art (`delta_liste`, höchstens 2.000).

### Auswahl

Die Oberfläche schickt nur, was ausgeschlossen ist: Pfade von Ordnern oder Dateien, dazu den Schalter „ohne nur online“. `Register::auswahl_bilden` liest danach alle Dateien mit anstehendem Schritt und nimmt die ausgeschlossenen heraus. `auswahl_setzen` begrenzt die vier Schritte auf diese Dateien. Nach dem Lauf wird die Begrenzung aufgehoben, auch nach einem Fehler.

Nicht gewählte Dateien kommen mit Namen ins Register, werden aber nicht verarbeitet. Beim nächsten Öffnen stehen sie wieder angehakt im Baum.

### Verarbeiten

`registerwerk_core::verarbeiten`:

1. Dateibaum durchlaufen, `aufnehmen` (nichts entfernen)
2. Auswahl bilden
3. „nur online“-Dateien der Auswahl laden
4. Inhalte lesen, Vorschauen erzeugen, Text erkennen, in PDFs schreiben, jeweils nur für die Auswahl
5. die in diesem Lauf geladenen Dateien zurück auf „nur online“
6. Suchindex nachführen (in der Tauri-Hülle)

„Anhalten“ greift nach der laufenden Datei. Nach einem Anhalten wird nicht zurückgestellt.

Das Schreiben in die PDFs braucht hier keinen zweiten Klick. „Verarbeiten“ gilt als Freigabe.

### Laden

- Vier Fäden fordern die Dateien an. Unter macOS über `registerwerk-macos::anfordern`, also `NSFileCoordinator.coordinate(readingItemAt:)`. Danach wird ein Byte gelesen.
- Der Hauptlauf prüft alle 0,5 s, welche Dateien eine Größe haben. Angekommene Dateien kommen sofort ins Register (`geladen_eintragen`: Größe, Datum, nicht mehr nur online).
- Das Warten endet, wenn alle da sind, nach 2 Minuten ohne neue Datei (`LADEN_WARTEN`), mit „Nicht warten, weiter“ (`laden_ueberspringen`) oder mit „Anhalten“.
- Danach nehmen die Fäden keine neue Datei mehr. Eine laufende Anforderung endet von selbst, die Datei kommt beim nächsten Lauf ins Register.
- Die Anzeige zeigt „x von y da“ und die Datei, auf die gewartet wird.

### Zurück auf „nur online“

`ablauf::auslagern` ruft `onlineonly online -w -t 300` für die in diesem Lauf geladenen Dateien auf, 50 Pfade je Aufruf. Aus der Ausgabe (je Zeile Zustand und Pfad) werden die Dateien mit `online-only` als ausgelagert eingetragen (`nur_online = 1`, Größe und Datum bleiben). Gesucht wird das Werkzeug unter `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin` und im `PATH`. Eine Anwendung aus dem Finder hat Homebrew nicht im `PATH`, deshalb die festen Orte zuerst. Fehlt es, wird der Schritt übersprungen, und die Oberfläche nennt den Befehl zur Installation. Exit-Code 69 bedeutet „Dropbox nicht erreichbar“.

### Scheiben aufteilen

- `SCHEIBE_GRENZE` 200 MB statt 1,5 GB.
- `Register::scheiben_aufteilen`: Für jede Scheibe über der Grenze mit mehr als einer Datei bleiben die ältesten Vorschauen bis zur Grenze. Die übrigen wandern in Paketen von höchstens 16 MB in neue Scheiben, nach Erfassungsreihenfolge, die Vorschauen einer Datei zusammen. Reihenfolge wie beim Speichern: Bild in die neue Scheibe, Verweis umhängen, alte Bilder über `vorschau_weg` löschen.
- Die Scheibe ist zum Verkleinern vorgemerkt (Merkmal `verdichten:N`). Erst wenn sie unter der Grenze liegt, läuft `VACUUM`. Ein angehaltener Lauf macht beim nächsten Aufruf weiter.
- Zu Beginn räumt der Lauf Bilder ohne Verweis aus der jüngsten Scheibe.
- Der Knopf im Datenbank-Symbol erscheint nur, wenn `aufteilen_noetig()`.

### Belegung des Registers

Es läuft höchstens ein schreibender Vorgang. Die Prüfung beim Öffnen belegt das Register für einige Sekunden. Ein Vorgang, der in dieser Zeit beginnt, wartet jetzt auf das Ende der Prüfung (`Lesen::belegen`, höchstens 2 Minuten), statt mit „Es läuft bereits ein Vorgang“ abgewiesen zu werden. Läuft ein echter Vorgang, überspringt die Prüfung und meldet das.

Die Oberfläche startet höchstens eine Prüfung zur selben Zeit. React fragt im Entwicklungsmodus beim Start doppelt, das führte anfangs zu einer falschen Meldung.

### TIFF mit Farbpalette

`tiff` liest keine Bilder mit `PhotometricInterpretation` 3 (RGBPalette). Der eigene Leser in `bild.rs` liest die erste Seite mit 1, 2, 4 oder 8 Bit je Pixel, ungepackt, PackBits, LZW (`weezl`, dieselbe Bibliothek nutzt `tiff` intern) oder Deflate, und setzt die Farben aus der `ColorMap`. Vier Testbilder liegen unter `tests/daten/palette_*.tif`.

### Platzhalter des File Providers

`dateibaum::lokale_groesse` meldet 0 für Dateien mit dem Kennzeichen `SF_DATALESS` (0x40000000 in `st_flags`). Alle Stellen, die vor dem Öffnen die Größe prüfen, nutzen diese Funktion: Dateibaum, „Ordner prüfen“, Inhalte, Vorschauen, OCR, Laden. Ohne das würden Platzhalter von Google Drive und OneDrive beim Lesen still geladen, weil sie ihre echte Größe melden.

### Oberfläche

- `src/register/Ablauf.tsx` ist der neue Reiter „Register“. `App.tsx` hält ihn immer geladen, damit die Prüfung beim Start läuft, und zeigt die Zahl am Reiter.
- Neue Prüfung beim Wechsel in den Reiter, wenn die letzte älter als eine Minute ist, und nach jeder Änderung an anderer Stelle (`registerwerk:geaendert`).
- Baum: Haken mit Zwischenzustand, Marken „neu“, „geändert“, ☁. Marken und Zahlen öffnen das Dateifenster für den Ordner.
- Schritte: eine Liste mit Zeichen (offen, läuft, fertig), Fortschrittsbalken und Ergebnis je Schritt.
- Die bisherige Ansicht (`Verwaltung.tsx`) steht eingeklappt unter „Einzelheiten und einzelne Schritte“.

### Build-Ordner

`cargo clean` löscht den ganzen Build-Ordner, auch seine Markierung „von der Dropbox ausgenommen“. `.cargo/config.toml` legt den Build-Ordner deshalb auf `target/cargo`. `target` bleibt stehen, `tools/dropbox_ausschluss.sh` ist unverändert.

## 4. Vorgehen

1. Zuschnitt: zuerst kleinere Scheiben, dann Delta-Lauf, dann Laden und Auslagern.
2. Scheiben: Kern mit Tests, Probe in Originalgröße in der Cloud-Umgebung, `pdf_pruefen --aufteilen` für die Probe bei Kim, dann der Knopf.
3. TIFF mit Farbpalette nach Kims Fehlerliste.
4. Delta-Lauf: Kern (Modi, Delta, Auswahl), Befehle, Oberfläche. Nach Kims erstem Blick: Dateifenster für jede Zahl, Kachel „nur mit Namen“.
5. Laden: Erster Ansatz (ein Byte lesen) lud nichts. Mit Kim im Terminal gemessen (`head`, `open`, Dateikoordination, Quick Look). Dateikoordination eingebaut, Warten auf gemeinsames Warten umgebaut, „Nicht warten, weiter“ und Schalter für „nur online“.
6. Zurück auf „nur online“: `onlineonly` von Kim installiert und an einer Datei getestet, dann eingebaut.
7. Platzhalter des File Providers, Build-Ordner, Belegung beim Warten auf die Prüfung.

Geprüft wurde in der Cloud-Umgebung (Tests, `cargo check` auch für macOS, Clippy, Oberfläche mit Testdaten in Chromium und WebKit) und von Kim in der Anwendung auf dem Notebook.

## 5. Entscheidungen

| Thema | Entscheidung | Grund |
|---|---|---|
| Scheibengrenze | 200 MB | praktikable Größe für den Abgleich mit der Dropbox (Kim) |
| Aufteilen | Knopf im Datenbank-Symbol | einmaliger großer Upload, Kim wählt den Zeitpunkt |
| Reiter „Register“ | aufgeräumter Ablauf, alte Ansicht eingeklappt | die bisherige Ansicht war informativ, aber überladen (Kim) |
| Vorauswahl | alles angehakt, auch „nur online“ | neue Belege kommen täglich und liegen meist nur online |
| Dateien ansehen | Klick auf jede Zahl | Kim will sehen, was gefunden wurde |
| Verarbeiten | entfernt nichts | Entfernen bleibt mit Rückfrage und Liste |
| Schreiben in PDFs | ohne zweiten Klick im Delta-Lauf | Textebene wird nur angehängt, im Pilot ohne Probleme (Kim) |
| Laden | Dateikoordination von macOS | einziger gemessener Weg ohne Fenster |
| Warten | gemeinsam, 2 Minuten ohne Fortschritt, „Nicht warten, weiter“ | Warteschlange oder offline dürfen den Lauf nicht aufhalten, es soll für den Anwender sichtbar sein (Kim) |
| „Nur online“ auslassen | ein Schalter über dem Baum | Planen vor dem Lauf mit einem Klick (Kim) |
| Zurück auf „nur online“ | `onlineonly`, nur für selbst geladene Dateien | keine Handarbeit danach (Kim). Bewusst lokale Dateien bleiben lokal |
| Unterstützte Cloud-Speicher | vollständig nur die klassische Dropbox | Laden und Auslagern nur dort möglich. In Doku und auf der Webseite deutlich nennen (Kim) |
| File Provider | Platzhalter erkennen, nicht ungefragt laden | Schutz vor stillen Downloads (Kim) |
| Ordner-Reiter | Umbau in v0.0.9 | Kim |

## 6. Bekannte Einschränkungen und Annahmen

- **Korrektur:** Das Konzept nahm an, dass Öffnen den Download auslöst. Bei der klassischen Dropbox lädt einfaches Lesen nichts. Für frühere Versionen hat das keine Folgen: Registerwerk öffnet „nur online“-Dateien seit v0.0.2 ohnehin nicht.
- **`onlineonly`** nutzt eine undokumentierte Schnittstelle der Dropbox-App. Ein Update kann sie brechen. Dann bleiben die Dateien lokal und die Anzeige meldet es.
- **Laden bei anderen Anbietern** (File Provider) ist nicht gemessen. **Annahme**: Lesen löst dort den Download aus.
- **`SF_DATALESS`** ist nur gebaut, nicht an einem echten Ast von Google Drive oder OneDrive geprüft.
- **Leere Dateien** (0 Byte) gelten weiter als „nur online“. Das Laden wartet auf sie vergeblich bis zum Ende der Wartezeit und meldet sie als nicht angekommen.
- **Angehaltener Lauf:** Bereits geladene Dateien bleiben lokal, sie werden nicht zurückgestellt.
- **Prüfung beim Öffnen** belegt das Register einige Sekunden (bei rund 100.000 Dateien). Die Dauer wächst mit dem Bestand.
- **Reiter „Ordner“** hat noch das alte „Dateibaum einlesen“ mit eigener Rückfrage.
- **Register im Cloud-Ordner** weiter unverschlüsselt und ohne Sperre.

## 7. Werkzeuge

- `pdf_pruefen --aufteilen <Register-Ordner>`: kopiert das Register nach `target/aufteilen_probe/`, teilt dort die Scheiben und vergleicht jede Vorschau vorher und nachher. Braucht Platz für eine Kopie.
- `onlineonly` (fremd, MIT, `brew install zamua/tap/onlineonly`): von Registerwerk aufgerufen, wenn installiert.
