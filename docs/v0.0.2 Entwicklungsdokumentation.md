# Registerwerk v0.0.2: Entwicklungsdokumentation

Stand: 16.11.2026. Diese Datei hält fest, was Version 0.0.2 enthält, wie sie entstanden ist und welche Entscheidungen dabei gefallen sind. Die übergreifenden Festlegungen stehen im [Konzept](konzept.md). Konkrete Pfade stehen nicht hier, sondern in `docs/intern/` (nicht versioniert).

## 1. Ziel der Version

v0.0.2 öffnet erstmals die PDFs und bringt ihren Text je Seite ins Register. Im Stufenplan des Konzepts (Abschnitt 14) ist das der zweite Schritt von Stufe 1.

| Enthalten | Nicht enthalten |

| PDFium angebunden, Ladeskript für die Bibliothek | Vorschauen |
| Text je Seite im Register | Suchindex und Suche |

| Datum aus PDF-Metadaten und Änderungsdatum | Verschlüsselung |
| Verarbeitungsstand je Datei, Fortsetzen nach Abbruch | Automatisches Laden von "nur online"-Dateien |
| Fortschritt und Anhalten in der Oberfläche | Bündeln von PDFium ins Programmpaket |
| Prüfwerkzeug `pdf_pruefen` | |

| Dauer | 26,9 s einschließlich Schreiben ins Register, reine Textauslese 1,4 bis 3,8 ms je Seite |
| Seiten mit Text | 89 %. 1.185 Seiten ohne Text, davon 1.030 Scans und 155 digital |
| PDFs ganz ohne Text | 93 (2,7 %) |
| PDFs mit schwachem Text (unter 60 % Güte) | 425 (13 %), 981 Seiten |

| Dokumentdatum | 93 % aus dem Dateinamen, 94 aus der PDF, 142 aus dem Änderungsdatum |

Die Werte decken sich mit der Stichprobe der Konzeptphase (Abschnitt 13): 15 % schwache PDFs erwartet, 13 % gemessen. Der Anteil der Scan-PDFs liegt bei 78 % statt 84 %. Seiten und PDFs sind dabei nicht vergleichbar, weil digitale PDFs im Mittel mehr Seiten haben.

Hochgerechnet auf rund 500.000 Dokumente braucht die Textauslese gut eine Stunde, ohne die Ladezeit aus der Cloud.

### Befunde aus den Stichproben

- **Seiten ohne Text sind meist Scans ohne OCR.** Geprüft an drei Beispielen: ein Strafzettel von 2017 ohne OCR-Ebene, die zweite Seite einer Bahncard-Quittung ohne OCR, ein Kontoauszug. Drei Viertel der 1.030 Scan-Seiten ohne Text stecken in 84 PDFs ohne jeden Text, darunter Fotoalben, Karten und Ausweise.
- **Kontoauszug 2017 hat gar keine Textebene.** Die Datei gilt als digital (kein ganzseitiges Bild). Aussehen und Kopfzeile sprechen für einen Ausdruck aus dem Online-Banking, bei dem die Schrift zu Kurven wurde. Der offene Punkt im Konzept ist damit für diese Datei beantwortet: kein Zeichensalat, sondern kein Text. Die Behandlung bleibt Fall 3.
- **Eine beschädigte PDF** im Bestand meldete PDFium als `FormatError`. Kim hat sie aus einer Sicherung ersetzt.

## 3. Aufbau

```
crates/registerwerk-core/src/
    pdf.rs          PDFium einbinden, Text, Bildanteil und Erstellungsdatum lesen
    guete.rs        Gütemaß: Anteil wortartiger Tokens
    inhalte.rs      Lauf über die ausstehenden PDFs, Fortschritt, Abbruch
    register.rs     Schema 2, Verarbeitungsstand, Kennzahlen
    datum.rs        zusätzlich PDF-Datum und Änderungsdatum
src-tauri/src/main.rs  Befehle inhalte_lesen und inhalte_abbrechen, Suche nach PDFium
src/                   Karte "Inhalte der PDFs", Fortschritt, Kennzahlen
tools/pdfium_holen.sh  lädt PDFium nach bibliotheken/pdfium/
tools/pdf_pruefen/     Prüfwerkzeug auf Basis des Kerns
```

### PDFium

- Rust-Anbindung `pdfium-render` 0.9.5 mit dem Feature `pdfium_8125`. Die Bibliothek wird zur Laufzeit geladen.
- Die Bibliothek selbst kommt aus den fertigen Builds von bblanchon/pdfium-binaries, Version `chromium/8125`. `tools/pdfium_holen.sh` lädt sie samt Lizenztexten nach `bibliotheken/pdfium/`. Der Ordner ist per `.gitignore` ausgeschlossen. Version im Skript und Feature in `Cargo.toml` immer gemeinsam ändern.
- Die Anwendung sucht PDFium in dieser Reihenfolge: Umgebungsvariable `REGISTERWERK_PDFIUM`, Ressourcen des Programmpakets (`pdfium/`), `bibliotheken/pdfium/lib` ab Arbeitsverzeichnis oder Programm aufwärts.
- Lizenz: PDFium steht unter BSD-3-Clause, die enthaltenen Fremdbibliotheken unter freizügigen Lizenzen. Eine MIT-Lizenz für Registerwerk ist möglich. Beim Weitergeben des Programmpakets sind die Lizenztexte beizulegen.

### Register, Schema 2

- Neue Tabelle `seite`: Text, sichtbare Zeichen, Tokens, wortartige Tokens und Bildanteil je Seite. Gespeichert werden die Zähler, nicht die Güte, damit sich Seiten zu Dokumenten zusammenfassen lassen.
- Neue Spalten in `datei`: Stand beim Lesen (Änderungsdatum und Größe), Verfahrensversion, Fehlermeldung, Seitenzahl, PDF-Erstellungsdatum als Rohwert.
- Jede Datei hat jetzt ein Dokumentdatum. Ohne Datum im Namen gilt das PDF-Erstellungsdatum, sonst das Änderungsdatum.
- Die Umstellung von Schema 1 läuft beim ersten Öffnen. Die Schema-Version wird innerhalb einer sperrenden Transaktion gelesen, damit gleichzeitiges Öffnen nicht doppelt umstellt.
- Wird eine Datei aus dem Register entfernt, gehen ihre Seiten mit (`ON DELETE CASCADE`).

### Wann eine PDF gelesen wird

Eine PDF steht aus, wenn sie noch nie gelesen wurde, wenn Änderungsdatum oder Größe vom Stand beim Lesen abweichen oder wenn die Verfahrensversion (`INHALT_VERFAHREN`) erhöht wurde. Der Wechsel auf "nur online" ändert nichts daran. Eine Datei mit Lesefehler wird erst nach einer Änderung erneut versucht.

### Gütemaß und Seitenart

- Tokens sind durch Leerraum getrennt, Satzzeichen am Rand zählen nicht. Wortartig sind Wörter aus mindestens zwei Buchstaben (auch mit Bindestrich) sowie Zahlen, Daten und Beträge.
- Eine Seite ist "ohne Text" unter 20 sichtbaren Zeichen, "schwach" unter 60 % Güte. Eine PDF ist schwach, wenn ihre Güte über alle Seiten unter 60 % liegt.
- Eine Seite gilt als Scan, wenn Bilder mindestens 70 % der Fläche abdecken. Bilder in Formularobjekten werden mitgezählt.

## 4. Vorgehen

1. **Zuschnitt und Klärungen** mit Kim: PDFium über `pdfium-render`, nur lokal vorhandene PDFs, Suchindex erst mit der Suche, Verarbeitungsstand je Datei.
2. **Versuch mit PDFium** als eigenes kleines Programm, auf dem Notebook gegen den Pilotbestand. Dabei Scan-Erkennung verfeinert und drei Beispiele von Kim in der Vorschau prüfen lassen.
3. **Kern mit Tests**, dann Tauri-Befehle, dann Oberfläche.
4. **Vorprüfung in einer Linux-Umgebung** mit dem Linux-Build von PDFium und erzeugten Test-PDFs. Sichtprüfung der Oberfläche mit Beispieldaten im Browser, hell und dunkel.
5. **Lauf auf dem Notebook.** Dabei fiel die doppelte Schema-Umstellung beim Start auf (siehe Entscheidungen).
6. **Versuch zum Prüfwerkzeug umgebaut** und nach `tools/pdf_pruefen` verschoben.

### Prüfwerkzeug

`tools/pdf_pruefen` liest PDFs mit dem Kern, ohne das Register anzufassen. Nützlich nach einem PDFium-Update, auf einem neuen Gerät oder für einzelne Problemdateien.

```
cargo run --release -p pdf_pruefen -- --still <Ordner>       Zusammenfassung
cargo run --release -p pdf_pruefen -- --ohne-text <Ordner>   PDFs mit Seiten ohne Text
cargo run --release -p pdf_pruefen -- --text <PDF>           Anfang des Textes zeigen
```

## 5. Entscheidungen

| Thema | Entscheidung | Grund |
|---|---|---|
| Anbindung von PDFium | `pdfium-render`, Bibliothek zur Laufzeit geladen, Builds von bblanchon | verbreitete Anbindung, fertige Builds für alle Zielsysteme |
| PDFium im Repo | nein, per Skript geladen, Version fest eingetragen | keine Binärdateien im Repo, reproduzierbarer Stand |
| "Nur online"-Dateien | werden nicht geöffnet und bleiben ausstehend | Öffnen löst den Download aus. Für die Erstindizierung macht Kim die Ordner von Hand offline verfügbar, das Laden im Delta-Lauf folgt in Stufe 4 |
| Eigener Knopf zum Laden | nein | entspricht dem Vorgehen bei der Erstindizierung, das automatische Laden kommt mit dem Delta-Lauf |
| Suchindex | erst mit der Suche | die Wahl hängt an der fehlertoleranten Suche, die Texttabelle ist die Grundlage |
| Verarbeitungsstand | Änderungsdatum und Größe beim Lesen, dazu eine Verfahrensversion | geänderte Dateien und geänderte Verfahren werden gezielt neu gelesen, ein Abbruch kostet nichts |
| Lesefehler | im Register festhalten, erst nach einer Änderung neu versuchen | sonst würde jede beschädigte Datei bei jedem Lauf erneut gelesen |
| Seitenart | Bildanteil je Seite speichern, Schwelle 70 % | fast kostenlos beim Lesen, wird für OCR-Fall 3 gebraucht |
| Dokumentdatum | für jede Datei, Quelle wird mitgespeichert | Konzept Abschnitt 9 vollständig umgesetzt |
| Schema-Umstellung | Version innerhalb einer sperrenden Transaktion lesen | die Oberfläche fragt beim Start im Entwicklungsmodus doppelt ab. Der zweite Zugriff versuchte die Umstellung erneut und meldete "duplicate column" |
| Versuch zu PDFium | als `tools/pdf_pruefen` behalten, auf den Kern umgebaut | nützlich für Prüfungen ohne Register |

## 6. Bekannte Einschränkungen und Annahmen

- **PDFium ist nicht im Programmpaket.** Die Anwendung findet die Bibliothek im Projektordner. Für ein fertiges Paket muss sie als Ressource unter `pdfium/` beigelegt werden, samt Lizenztexten.
- **Datum aus dem Änderungsdatum** wird als Kalendertag in UTC gespeichert. Um Mitternacht kann es um einen Tag abweichen.
- **Datum aus der PDF** übernimmt nur den Kalenderteil, Uhrzeit und Zeitzone werden nicht ausgewertet.
- **Gütemaß ist grob.** Ob die Schwelle von 60 % trifft, zeigt sich erst mit der OCR in Stufe 5.
- **Seiten ohne Text** schließen leere Rückseiten ein. Sie werden später per OCR geprüft und bleiben ohne Text.
- **Register unverschlüsselt.** Es enthält jetzt den Volltext. Die Verschlüsselung folgt in Stufe 3, die Arbeitskopie liegt bis dahin nur lokal im Benutzerprofil.
- **Nur macOS geprüft**, Windows und Linux als Zielsysteme nicht.
